# ADR-004: Agent contract — A2A-inspired HTTP contract behind an adapter

- **Status:** Accepted (2026-11-24, with amendments C1–C3; C4, C5 parked)
- **Date:** 2026-11-24
- **Spec refs:** §8.2, §8.3, §12.2
- **Reference:** A2A Protocol Specification v1.0.0 (https://a2a-protocol.org/latest/specification/), reviewed 2026-11-24

## Context
v1.0 claimed A2A, but its example payloads were a custom JSON shape. v1.1 replaced that with "A2A-inspired, mapped 1:1 to A2A concepts". Checked against A2A v1.0.0, that 1:1 claim doesn't hold either: three of our core design choices diverge on purpose. Claiming compliance, or a 1:1 mapping, without either being true violates the spec's own rules (§19.1 rule 16).

## Decision
- Use a small versioned REST contract (`/v1/tasks`, `/v1/tasks/{id}`, `/v1/tasks/{id}/cancel`, `/.well-known/agent-card.json`), defined as Pydantic models in `contracts/a2a/`.
- The transport is isolated in `apps/orchestrator/delegation/` behind a `TaskTransport` interface.
- Documentation says "A2A-inspired" and never "A2A-compliant".

### Amendments accepted at sign-off
- **C1: An honest mapping instead of "1:1".** The mapping below, including the deliberate divergences, is the contract for any future A2A adapter.
- **C2: Separate agent and orchestrator task enums.** The agent API exposes **agent task status** only, using A2A `TaskState` names: `SUBMITTED`, `WORKING`, `COMPLETED`, `FAILED`, `CANCELED`, `REJECTED`. Orchestrator-only states (`PENDING`, `DISPATCHED`, `TIMED_OUT`) live in orchestrator SQLite. The status mapping is in spec §8.2. `REJECTED` covers a policy refusal at submit (unknown `task_type`, ceiling above clearance) and is never re-dispatched.
- **C3: Agent Card at A2A's well-known path,** `/.well-known/agent-card.json`. The card content keeps our minimal shape for now (see C4).
- **C4 (parked, Good-to-have):** shape the card like A2A's required fields (`name, description, supportedInterfaces, version, capabilities, defaultInputModes, defaultOutputModes, skills`), with `clearance` in an extension.
- **C5 (parked, Good-to-have):** rename cancel to `POST /v1/tasks/{id}:cancel`, matching A2A's REST binding and our own `findings:batch` style.

### Mapping to A2A v1.0.0
| Concept | A2A v1.0.0 | Nexus | Adapter rule |
|---|---|---|---|
| Discovery | Agent Card at `/.well-known/agent-card.json` | Same path; minimal card | Expand the card (C4) when adopting the SDK |
| Submit | `POST /message:send` (REST binding) | `POST /v1/tasks` | Wrap the task request in a Message with one data part plus extension metadata |
| Get | `GET /tasks/{id}` | `GET /v1/tasks/{id}` | Path prefix only |
| Cancel | `POST /tasks/{id}:cancel` | `POST /v1/tasks/{id}/cancel` | Path style (C5) |
| Grouping | `contextId` | `investigation_id` | 1:1 |
| Client dedup | `messageId` (optional) | `(task_id, attempt)` | `messageId = {task_id}:{attempt}` |
| States | `SUBMITTED, WORKING, COMPLETED, FAILED, CANCELED, REJECTED, INPUT_REQUIRED, AUTH_REQUIRED` | Agent status uses the first six | `INPUT_REQUIRED` / `AUTH_REQUIRED` unused in P0 |
| Results | Artifacts made of Parts | Flat `TaskResult` JSON | One Artifact with one data part |
| Custom fields | `metadata` + extensions declared in the card | Top-level `attempt`, `deadline`, `token_budget`, `classification_ceiling`, `trace_context` | Carried under an extension URI, e.g. `urn:nexus:task:v1` |

### Deliberate divergences (an A2A SDK adapter must handle these)
1. **Task IDs are generated by the client (orchestrator).** A2A generates task IDs on the server and doesn't let a client supply one for a new task. Our restart recovery, re-dispatch and commit idempotency (ADR-003, spec §8.5) all key on the orchestrator's `task_id`. An adapter must keep a `nexus task_id ↔ A2A task id` map, persisted in orchestrator SQLite.
2. **Attempt, deadline and token budget semantics** are not in A2A. They travel as extension metadata; a third-party A2A agent would ignore them, so the orchestrator still enforces deadlines and budgets itself.
3. **Flat results** instead of Artifacts.

## Alternatives considered
| Option | Pros | Cons |
|---|---|---|
| **A2A-inspired REST with documented mapping (chosen)** | Simple; under our control; honest; the adapter path is spelled out | Not interoperable with third-party A2A agents |
| Official A2A SDK from day one | Real interoperability; standard Agent Cards | Server-generated task IDs fight our idempotency/recovery model; no P0 consumer needs interoperability |

## Consequences
- (+) Fast to build and test; honest claims; the P1 swap has a written checklist (the divergences above).
- (+) Agent status names already match A2A, so status mapping in a future adapter is trivial.
- (−) Two spellings meet at one boundary (wire `CANCELED`, orchestrator `CANCELLED`); the §8.2 mapping is the only crossing point.
- (−) Swapping to the official SDK later (P1) is an adapter rewrite plus an ID map and contract-mapping tests.
